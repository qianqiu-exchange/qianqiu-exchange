# 千秋交易所（History Exchange）— 可执行产品需求文档

> **版本**：V1.0 / 2026-10-28  
> **产品形态**：开源、离线优先、单机、回合制历史人物交易策略游戏  
> **交付目标**：Codex 可基于本 PRD 分阶段实现一个可玩、可验收、可复现的 MVP。  
> **产品标语**：在历史尚未发生之前，买入你相信的人。

## 0. 结论与不可变约束

- **核心乐趣**：分析历史情报、选择人物与事件资产、低买高卖、管理风险、击败 NPC，并经历历史揭晓。
- **玩法固定**：玩家主动点击「推进历史」；现实时间不驱动游戏；回合内市场只有玩家下单才改变，推进时 NPC 按确定顺序下单，之后到期结算。
- **市场固定**：二元 YES/NO 事件合约是唯一基础定价源；人物股是合约的可交易打包资产，不存在独立随机股价。
- **离线固定**：无账户、无服务器、无付费、无真实货币、无真实资金奖品；核心引擎不使用 LLM。首次安装/缓存后可离线玩，长期可通过 Tauri 打包为完全离线桌面应用。
- **开源固定**：核心逻辑为纯 TypeScript 包；剧本为版本化 JSON；存档和交易日志可导入/导出；UI 不得包含成交或结算的权威逻辑。
- **公平性声明**：真实历史的结局在现实中已知。本游戏是“历史回放交易策略游戏”，不是预测尚未发生事件的真实市场；不得宣传能够防止玩家提前知道历史答案。单机记录可修改，不是防作弊权威排行。

## 1. 目标、成功标准、非目标

### 1.1 用户故事
1. 作为玩家，我能在断网情况下从主菜单开始一局三国剧本，收到 1,000 枚游戏币。
2. 我能查看当前年份可获知的信息、人物页、YES/NO 价格、人物股价格、持仓和风险。
3. 我能在确认报价后买入/卖出合约或人物股，交易立即真实影响同一局内的市场价。
4. 我能点击推进历史，看到 NPC 交易记录、市场变动、到期结算和历史依据。
5. 我能存档、关闭游戏、恢复到完全相同的状态；或以同一随机种子重放一局。
6. 作为贡献者，我能新增经过校验的剧本，不修改交易引擎。

### 1.2 首发指标（产品假设，不是行业基准）
- 从主菜单到首笔成交 ≤ 3 分钟；25–40 分钟完成首局。
- 试玩用户 ≥ 70% 完成一局，≥ 40% 主动重开一局，≥ 80% 能正确理解“人物股由事件合约组成”。
- 引擎成交/结算账本一致性测试全通过；固定种子跨多次运行输出一致。
- 首次完整载入后，关闭网络可启动、交易、推进、结算和导出存档。

### 1.3 V1 不做
真实金钱、充值提现、全球排名、多人联机、用户注册、在线行情、限价簿、杠杆/借贷、做空未持有合约、PVP、AI API 必需依赖、无限开放人物自动生成、故事分支改写真实历史。

## 2. V1 内容边界与回合时间轴

**剧本**：《三国：群雄逐鹿》，ID `three-kingdoms-207`，内容版本 `1.0.0`。

- 核心人物：曹操、刘备、孙权、诸葛亮（4 位）。
- NPC：价值型、趋势型、情报型、噪声型（4 名）。
- 市场：8 个 YES/NO 合约；每位人物有 1 个打包人物股。
- 回合：`207 → 208 → 214 → 220 → 221 → 223 → 229 → 234`（8 回合）；“跨年”是剧情跳跃，不表示现实流逝时长相同。
- 公开线索：每回合开盘时仅展示该时点**之前**已经发生且允许公开的背景信息；回合结束才揭晓该回合到期事件。禁止在当回合开盘的新闻中提前写出当回合结算结果。之所以保留 220、221、229 等独立回合，是为了避免跨年跳跃把早已发生的事实留在尚可交易的合约里。

每个年份表示该公历纪年**年初开盘、年末结算**的抽象时间窗；不用于宣称古代事件恰好发生在现代公历 12 月 31 日。跨年时只揭示上一轮终局已发生的事实；所有 `settleRound` 早于本轮的合约均已关闭并完成结算，不能再次买卖。

### 2.2 每轮状态机
`NOT_STARTED → ROUND_REVEAL → PLAYER_TRADING → NPC_EXECUTION → MARKET_SETTLEMENT → ROUND_SUMMARY → (下一轮 ROUND_REVEAL | GAME_FINISHED)`。

1. `ROUND_REVEAL`：加载该轮公开资讯，检查市场开启/关闭，展示情报；禁止读取未来新闻作为界面内容。
2. `PLAYER_TRADING`：玩家最多 **5 笔成功执行的订单**；预估报价、被拒订单不占次数；可随时结束交易阶段。
3. `NPC_EXECUTION`：四名 NPC 各最多提交 2 笔订单；执行顺序由固定 PRNG 决定，订单逐一以**最新市场状态**报价执行；NPC 不得跳过余额、持仓与价格校验。
4. `MARKET_SETTLEMENT`：到期市场立即禁止新交易；按结果偿付全部 YES/NO 份额、清空对应合约持仓，并更新人物股分红和交易引擎状态。
5. `ROUND_SUMMARY`：展示公开新事实、NPC 交易明细、账户变动、人物资产股价与结算说明；下一轮开始前允许保存。
6. 终局：所有市场已结算；玩家和 NPC 根据终局金币余额排序；展示收益率、最大回撤、各轮资产变化、交易日志及史料回顾。

**边界规则**：当前回合正在执行时不允许二次点击推进；强退恢复采用最近一次完整提交的状态；若余额不足仍可推进；回合数不能倒退。非标准“练习回滚”另开存档分支，并在成绩中标记。

## 3. 金币与资产规则

### 3.1 钱包
- 玩家与每名 NPC 初始资金均为 `1,000.000000` 游戏币；不能充值、交易转账或借款。
- 金额使用整数微金币 `microCoins`（1 金币 = 1,000,000 微金币）持久化；份额使用整数微份额 `microShares`（1 份 = 1,000,000 微份额）。
- 玩家每单份额为 1–200 的**整数份人物股或事件合约**；人物股内部按权重拆分出的事件份额可以是小数。
- 只允许买 YES、买 NO、卖出已持有份额、买/卖人物股；不允许裸卖空、现金余额为负、账户间划转。
- 每单按成交额绝对值收取 `1%` 手续费；买入：`cashChange = -tradeCost - fee`，卖出：`cashChange = -tradeCost - fee`（卖出 `tradeCost < 0`），费用计入公共手续费池，不奖励玩家。
- 余额与份额精度为 1e-6；所有转账计算统一采用确定的舍入政策。任一订单只要有一条校验失败就全单回滚。

### 3.2 LMSR 定价（事件合约唯一基础市场）
对于每个事件 E：

`C(qY,qN) = b * log(exp(qY / b) + exp(qN / b))`

`pYES = exp(qY/b) / (exp(qY/b) + exp(qN/b))`；`pNO = 1 - pYES`。

- V1 全部合约以 `qY=qN=0` 初始化，价格分别为 0.5；`b=100` 为可配置、剧本固定的初始流动性参数。
- 订单交易成本 `delta = C(qAfter) - C(qBefore)`，买入 delta > 0，卖出 delta < 0；手续费 `fee=abs(delta)*0.01`。
- 实现必须使用数值稳定的 `logSumExp` 与 logistic/softmax，避免高份额指数溢出。
- `qY`,`qN` 是**市场向全部参与者净售出的累计份额**；买入增加、卖出减少，绝不是某一玩家单独持仓。
- 为保证市场可对任意交易流提供报价，每个市场设独立做市准备金。二元、初始 50% 的 LMSR 做市商最坏损失上界为 `b * ln(2)` ≈ `69.314718` 金币。V1 的财政账本必须显式分开玩家/NPC 钱包、做市准备金、累计交易成本与手续费池；不得声称玩家之间直接资金守恒。
- 用户提交订单时传入 `maxTotalDebit`（买）或 `minNetCredit`（卖）；实际执行重新报价，超出接受条件拒绝成交。
- 成交价格=整笔真实交易支付金额，不得用屏幕上显示的即时价格直接乘份额代替。

### 3.3 合约生命周期
`SCHEDULED → OPEN → CLOSED → SETTLED`，异常可进入 `VOID`。

- `OPEN` 可交易；`CLOSED` 无法交易但保留持仓；`SETTLED` 不能再次付款；`VOID` 回退这份市场的整段影响需要确定性的重算方案。
- 结算 YES 时：YES 每份兑付 1 金币，NO 每份兑付 0；结算 NO 反之。
- 必须有 `settlementId` 幂等约束，防止存档恢复后二次付款。
- V1 内容包只允许已人工核查、不会产生争议的事件上线。发现错误时将剧本版本废止，不在一局进行中的本地数据上静默改判；V1 不实现复杂历史争议仲裁。

### 3.4 人物股（真实可买卖的合成资产）
- 人物股不是单独发行、独立报价的证券，而是**预定义的事件权益篮子**：`bundle = [{eventId, side, weightBps}]`，每股权重之和等于 10,000 基点。
- 例：`刘备-LB` = `E01 YES 30% + E03 YES 40% + E04 YES 30%`。这只是剧本预定义的命题组合，**不能被称为历史人物客观价值**。
- 买入 `N` 人物股：对每个尚未结算的成分市场，以 `N*weightBps/10000` 的份额执行对应 YES/NO 买单；若任一腿资金不足、市场不可用或滑点超限，整个篮子订单拒绝，不出现部分成交。
- 卖出 `N` 人物股：只能卖出其自身仍持有的 bundle 单位；在所有尚未结算的基础市场卖出对应份额；不得占用玩家通过单独交易买入的份额。
- 事件结算时，人物股已持有者按持有份额收到对应成分的自动**分红**，该成分从以后的人物股买卖中移除。后续新买入者没有领取往期分红的权利。
- 因此人物股结算后的**除权价格**下降不代表投资亏损；界面必须同时展示“未结算部分价格”、“累计每股分红”和“累计回报（含分红）”，否则 K 线会误导玩家。
- 所有成分结算后，人物股无未结算价值；自动注销或标记完成，终局成绩仅通过已分配金币计算。
- **资金技术约束**：账户中将“单独事件持仓”和“人物股拆分持仓”分开记录归属；报价与风险估值按每个基础市场中的总份额聚合，以避免同一合约重复计价。

## 4. NPC 交易系统（不依赖大模型）

### 4.1 统一接口
NPC 使用与玩家**相同的 quote/execute/settle 引擎**；NPC 的差异仅在“决定交易什么”上。每轮最多 2 笔，交易失败不无限重试。

NPC 类型：
1. **VALUE** 价值型：比较自己对事件概率的信念值 `belief` 与市场价，价差足够覆盖手续费/滑点才买入；长周期、低周转。
2. **MOMENTUM** 趋势型：根据已发生的价格变化决定方向；设最大仓位和止损限额。
3. **NEWS** 情报型：只分析截至当前开盘可见的情报标签和可信度，修正自己对事件的概率估计。
4. **NOISE** 噪声型：使用固定种子的伪随机行为，提交受余额限制的小额订单；避免市场完全静止。

### 4.2 不许“历史先知”
- 决策函数输入只能包含 `publicInformationAtRound`、过去价格序列、本人钱包/持仓、人物和合约非结果字段、以及预设人格/偏好。
- 不可传入 `resolutionOutcome`、未来轮次情报、未来 NPC 决策或隐藏剧情表。使用白名单的 `NpcObservation` 视图而不是将整个场景对象传入。
- 本地文件最终包含事实结局，因此无法阻止玩家通过查看资源代码获得剧透；该限制只保证**代码模拟规则上**不作弊。
- 固定种子 `seed` + 固定剧本版本 + 同一操作序列必须得到完全相同的订单、市场状态和终局结果。

### 4.3 NPC 行为执行
每轮推进：用 PRNG 打乱 4 名 NPC 的执行顺序；每位 NPC 依据**交易前最新**报价生成最多 2 个意向；每笔意向均重新校验并成交；执行记录写日志。初始默认 NPC 风险参数要让玩家看到至少一次明显不同的策略选择。不能使用 `Math.random()`、系统时间或 AI 接口影响核心判定。

## 5. 前端交互与页面

### 5.1 信息架构
- `/` 开始页：新游戏、继续、导入存档、规则说明、设置。
- `/play` 交易终端：顶部赛季/当前年份/回合进度；左侧人物与市场列表；中央价格走势/资讯；右侧买卖与交易预览；底部最新成交和持仓。
- `/character/:id` 人物详情抽屉：简介、当时已知背景、人物股成分、相关事件、价格与累计分红、史料来源（只显示已解锁部分）。
- `/portfolio` 资产：余额、总资产、持仓、累计分红、历史盈亏、风险和逐轮表现。
- `/round-summary` 回合结算：历史新闻、合约结果、NPC 订单、奖励/损失、下一回合。
- `/result` 终局成绩：最后金币、回报率、最大回撤、NPC 对比、交易回放、分享为图片/JSON。
- `/library` 剧本：安装的内容包与校验状态（V1 内置一个）。

### 5.2 下单交互（必须有）
1. 选择市场或人物股 → 选择买/卖与方向 → 输入整数数量。
2. 立即预估 `总成本/净回收、手续费、成交后预计概率、钱包余额、当前持仓、最大可能到期亏损`。
3. 点击确认，交易引擎重新报价并校验 → 执行或显示明确失败原因。
4. 成功后，**同一局**相关合约及人物股价格立刻联动更新，记录新行情与账本。
5. 禁止市场关闭后点击买卖；提供键盘可达性、数值颜色之外的涨跌标识与移动端响应布局。

### 5.3 行情与可视化
- 每次有效成交新增真实市场价采样点；每回合可由成交序列生成 OHLC。没有成交则平盘，不编造涨跌。
- 组合股价格按**逐腿同时成交的净金额/份额**展示可执行成本，另可显示当前分量的加权中间价并明确区别。
- 含分红收益曲线和除权现价曲线必须分开标签，不能统一称“价格上涨”。
- 默认体验须避免“现实资金交易所”的误导：持续提示“虚拟金币、历史回放、单机模拟”。

## 6. 存档、可复现性和开放剧本

### 6.1 存档
- 存储方式：IndexedDB；Service Worker + 缓存静态资源；用户可导出/导入 JSON。
- 每局保留 `saveSchemaVersion`、`scenarioId/version/hash`、`engineVersion`、`seed`、`PRNG state`、`roundIndex`、`phase`、钱包、账户持仓、market q、结算标记、角色状态、历史行情、操作日志、账本。
- 存档写入应以“单次交易/完整推进阶段”的一致状态为事务边界；不允许余额已扣但持仓未加的半成品。
- 导入校验 schema、hash、非负余额与持仓、市场状态、重复结算 ID；错误时拒绝载入且保留原存档。
- 版本迁移只能明确维护 `migrations/`，无法迁移时显示只读旧存档导出选项。
- `Replay`: 从 seed + 完整操作日志重放，输出各轮状态 hash；与存档终局一致。不得将仅保存了最终状态的“继续游戏”伪称完整回放。

### 6.2 剧本内容格式
剧本包最少包括：
- `manifest.json`: `id`、`version`、`title`、`license`、`locale`、`roundIds`、`contentHash`、`credits`。
- `characters.json`: id/姓名/简介/阵营/素材路径/人物股 `bundleLegs`。
- `contracts.json`: id/问题/标准/开启回合/截止回合/结算 YES|NO/审校状态/史料 URL 与定位。
- `rounds.json`: year/公开新闻/情报标签/开放合约/结算合约。
- `npc-presets.json`: 策略类型、风险参数、公开信念先验；不可将未来结果暴露给决策函数。
- `assets/`: 必须具备版权许可及来源，缺失可使用通用占位插画。

**导入校验**：唯一 ID、引用存在、所有权重整数且总计 10000、结算轮次存在、开盘先于结算、成分市场存在、枚举合法、所有合约都有判定条件和证据、所有剧本资源在离线包内；错误输出到字段路径。

## 7. 推荐技术栈与模块划分

## 10. 明确的高风险项与止损策略

1. **历史已知结局**：不能让规则宣称完美信息公平；先定义为历史回放策略游戏。新玩家体验不足时，优先增加冷门历史剧本和信息分层；平行历史是后续独立模式。
2. **NPC 虚假刺激**：禁止无账本的随机 K 线；市场新闻本身不直接修改价格，必须有实际订单成交才能变价。
3. **人物股分红会导致“暴跌错觉”**：UI 强制分离除权价与总回报；测试结算前后财富变化。
4. **作者主观决定人物伟大程度**：人物股仅代表公开事件篮子及公开权重，不是“人格价值”、“历史真理”。
5. **LMSR 补贴与资金闭环**：设置并单独记账做市准备金，不能假设零成本真实清算。
6. **剧本版权与争议**：每条事件带来源，转载图片、史书翻译、AI 生成素材均核查许可；无来源不发布。
7. **游玩数据可篡改**：本地排行榜仅作娱乐，不向玩家展示“全网官方排名”。
8. **开发范围膨胀**：完成第一个 4 人物/8 合约/8 回合剧本前，不能启动云同步、付费、社交与大模型生成。

### 13.2 核心执行伪代码

```ts
function submitOrder(state: GameState, intent: OrderIntent): Result<GameState> {
  // 1. 验证当前 phase、market.status、orderId、交易次数和整数份额
  // 2. 验证账户持仓(卖)及资产篮子所有腿(若为人物股)
  // 3. 以当前市场净售出份额计算 LMSR 整笔成本与手续费
  // 4. 检查资金、maxTotalDebit/minNetCredit、数值精度
  // 5. 构建 wallet、position、market q、journal 和 actionLog 的新状态
  // 6. 以单个事务提交；全部成功或全部保持原样
  // 7. 返回最终报价、订单日志和新的状态哈希
}
```

**定义两种价格**：`indicativePrice` = 当前瞬时边际价格，适于行情展示；`executionQuote` = 此次指定数量整单执行的精确成本，适于确认和风险控制。不得混用。

**定义两种成绩**：`netWorth` = 可用金币 + 对全部持仓采用同一市场状态依次计算的清仓估算；`finalScore` = 全部合约实际结算后的剩余金币。若同一人物股与事件订单共享成分市场，应先聚合基础份额后估值，禁止对两者单独计算再相加。
